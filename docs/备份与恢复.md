# 备份与恢复

仅供 NAS 维护者使用。全库备份含所有个人账本、账号和加密 Token；`.env` 中的原密钥必须另行保存。网页管理员无下载和恢复权限。

## 先演练，不覆盖正式库

1. 生成备份并记下命令输出的文件名：

```sh
docker compose exec app python manage.py backup
```

`pg_dump` 使用自定义格式，成功后由 `pg_restore --list` 检查目录，再改为 `.dump` 后缀并清理超期文件。这个检查不能代替一次真正恢复。

2. 确认不存在名为 `gold_restore_check` 的数据库。下列名称专用于本次演练，不得换成正式数据库名。创建独立空库：

```sh
docker compose exec db sh -c 'createdb -U "$POSTGRES_USER" gold_restore_check'
```

3. 把下方的 `gold_实际文件名.dump` 替换为刚生成的文件名，在独立空库恢复：

```sh
docker compose run --rm --no-deps app sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" pg_restore --host=db --username="$POSTGRES_USER" --dbname=gold_restore_check --no-owner --exit-on-error /backups/gold_实际文件名.dump'
```

4. 使用只读查询检查演练库数据数量；通过 NAS 维护者自己的数据库工具核对初始现金、份额、流水和计划，并与正式库同一备份时点对照。不要将查询结果发布到日志或分享给应用管理员：

```sh
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d gold_restore_check -c "SELECT COUNT(*) FROM core_account; SELECT COUNT(*) FROM core_entry; SELECT COUNT(*) FROM core_plan;"'
```

5. 验证成功后，演练库是否删除由维护者确认；本交付不自动删除数据库。

## 正式恢复流程

1. 确认受影响用户与备份时点，知道备份后新增的记录需要补录。保存当前库的另一个独立备份。
2. `docker compose stop app`，保持 db 容器运行，停止网页写入与监测。
3. 根据上方流程恢复到一个**新的独立数据库名称**，先核对恢复数据。`docker compose run --rm --no-deps app ...` 只启动临时恢复命令，不启动网页或监测，所以正式 app 保持停止。不要向已有正式库直接执行 `--clean` 或覆盖恢复。
4. 在 `.env` 将 `POSTGRES_DB` 指向核对后的恢复库，并设置 `PAUSE_NOTIFICATIONS=1`。原正式库先保留。注意已有 PostgreSQL 数据目录不会因为更改环境变量自动创建或重置数据库。
5. `docker compose up -d --force-recreate`；应用执行必要迁移。确认健康检查、本人登录、本人账目、计划和 Token 解密正常。
6. 恢复会回到备份时的会话、计划与提醒状态。先核对备份后发生的实际成交和处理结果，避免把已经执行的旧计划再次视为待执行。`PAUSE_NOTIFICATIONS=1` 期间可登录核对，但不会创建或自动发送交易提醒。
7. 核对完毕后将 `.env` 的 `PAUSE_NOTIFICATIONS=0`，执行 `docker compose up -d --force-recreate app` 恢复监测；确认首页维护提示消失。

恢复前需演练一次。本次本机没有 Docker daemon / PostgreSQL 服务，**尚未进行真实恢复演练**。不要将单元测试的模拟备份当作恢复成功。
